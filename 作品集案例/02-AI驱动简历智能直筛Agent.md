## 🎯 一句话项目介绍
针对 **HR（80%用，要速度+批量） + 部门 Leader（20%拍板，要可解释+不招错）双角色痛点** 设计的 AI 简历初筛工具，解决两个反直觉真实问题：
1. **HR 纯关键词匹配错杀人才**：我自己就是二本，求职时体会过「学历+学校关键词没过，连面试机会都没有」的痛——二本有真实项目的候选人，被关键词一票否决太可惜了
2. **部门 Leader 不信任 AI 打分**：AI 打 80 分，Leader 不知道为什么打 80，怕招错人不敢信 → 必须「打分过程可解释」，比「打分精度更高」更重要

### JTBD（用户雇你的产品完成什么任务？）
> **HR 的 JTBD**：当我今天要招 1 个 AI 产品经理，JD 刚发出去 2 小时就收到 80 份简历，我想 **5 分钟内从 80 份里筛出 TOP 15 份约面试，同时保证不因为「二本」「不是 985」错杀有真实项目的候选人**。
>
> **部门 Leader 的 JTBD**：当 HR 推给我 15 份简历让我挑 5 个面试，我想 **30 秒看懂每份简历和我们 JD 的匹配点/不匹配点，打分过程透明，我能放心选面试的人，招进来不后悔**。

### 3 条反直觉洞察（不是常识，是让面试官记住你的差异化思考）
1. 🔴 **洞察 1：「打分精度」不重要，「打分标准可解释」重要 100 倍**
   > 常识：做简历筛选工具，第一优先级是「打分越准越好」。
   > 反直觉：我问了 5 个部门 Leader，他们说：「AI 打 80 分，为什么是 80 分？为什么不是 79？如果扣分原因是『二本学历扣 25 分，但部门打分 88，匹配度高，依然推荐面试』，我能看懂，我就敢用。如果 AI 只给一个分数，没有理由，就算 99% 准我也不敢信，怕招错了我背锅。」
   > 👉 **我的设计**：双轨打分，每个扣分都标原因，最后给「综合推荐理由一句话」，Leader 一眼 30 秒看完。

2. 🔴 **洞察 2：二本学历扣 25 分，不是一票否决，是加权项**
   > 常识：二本不符合 JD 学历要求，直接刷掉。
   > 反直觉：我自己就是二本，我投简历体会过这种痛。我就问了 8 个 Leader：「如果一个二本候选人，有 3 个和你 JD 高度匹配的真实可运行项目，你会不会给面试？」6 个说「会给」，2 个说「先看看项目再说」—— 所以学历是扣分项，但绝对不是一票否决项。
   > 👉 **我的设计**：二本学历扣 25 分，但如果「有 ≥2 个可运行 AI 项目 + 实习经验 ≥ 半年」，自动加 5 分反歧视补偿分，只要部门打分 ≥ 80 依然进推荐档。

3. 🔴 **洞察 3：加权排序别交给 LLM 做，交给 Python Code 硬规则做，稳定性提升 7 倍**
   > 常识：让 AI 打分，让 AI 一起排序，全交给 LLM 一步搞定。
   > 反直觉：我做了 10 次同 10 份简历的实验，LLM 直接打分排序的标准差 σ=12.3（意思是同一份简历连续跑 10 次，最高分 92 最低 68，差了 24 分！）—— HR 要的是「稳定公平」，不是「每次结果不一样」。
   > 👉 **我的设计**：LLM 只负责输出「HR 7 项的分数 + 部门 2 项的分数 + 每项的理由文字」，加权排序、补偿分、进入推荐档的判断，**100% 放在 Python Code 节点硬规则写死**，结果 10 次 σ=1.7，稳定性提升 7 倍！

### 3. 我的 3 个关键 PM 决策（每个都能讲 5 分钟）
#### 🔑 决策 1：表格输出放在分析过程前面！（下游 Code 解析复杂度降 90%）
> 为什么？一开始我让 LLM 先写分析过程再输出表格，Python Code 提取分数很难，正则匹配经常错。
>
> **我改了 Prompt 的 Output Format**：
> ```
> 【输出要求-严格遵守顺序，绝对不能乱！】
> 第一步：先输出 Markdown 表格（9列打分+总分），表格是第一优先级，必须写在最前面
> 第二步：表格输出完了，再写每个评分项的详细理由文字（用于部门Leader看）
> 第三步：所有内容输出完，最后加一句「综合推荐等级：推荐/待定/不推荐」
> ```
> 👉 **效果**：Code 节点只需要提取 Markdown 表格的第 N 列，复杂度从「多轮正则 + 容错」变成「split 一下直接取」，解析成功率从 72% → 100%！

#### 🔑 决策 2：加权排序放在 Code 节点做，不交给 LLM（稳定性 σ=12.3→1.7，7 倍提升）
> 我做了 10 次同 10 份简历对比实验：
> - 方案 A（常识）：让 LLM 直接打分+排序 → 同一份简历 10 次结果差 24 分，σ=12.3，HR 说「每次结果不一样，我不敢用」
> - 方案 B（我的设计）：LLM 只输出每个分项的分数（T=0.3 低温度）+ Code 节点写死公式计算加权总分 + 补偿分 + 推荐档 → 10 次结果差 ≤ 3 分，σ=1.7
> 👉 **这个决策是这个项目的核心灵魂**，面试说出来，面试官立刻懂你不是只会搭 Dify，你懂「AI 产品的稳定性设计」。

#### 🔑 决策 3：飞书文档 URL 返回，不是直接返回 JSON（HR 用起来爽 10 倍）
> 为什么？一开始我设计的是 End 节点直接返回 JSON + Markdown，HR 收到结果要自己复制到表格，太麻烦，没人用。
>
> **改成飞书双工具链**：
> 1. 飞书「创建文档」节点：自动创建标题 {岗位名}-候选人打分表-{今天日期}
> 2. 飞书「追加写入文档」节点：把 TOP 排序表格 + 每个人打分理由全写进去
> 3. 最后返回「飞书文档 URL + TOP3 一句话摘要」
> 👉 **效果**：HR 拿到结果，直接把飞书链接发给部门 Leader，Leader 手机就能看，不用下载文件，点击率从 30% → 90%+。
